# Tauri v2 as a desktop shell around a Node/TypeScript harness — research report

**Date:** 2026-09-16 · **Version baseline (verified today):** `tauri` **2.11.5**, `tauri-runtime-wry` **2.11.4** (pins `wry 0.56.0` with `linux-body` enabled), `tao 0.37.0`; `tauri-plugin-shell` 2.x, `tauri-plugin-updater` **2.11.0**; wry's latest published crate is 0.57.0 ([docs.rs/tauri](https://docs.rs/tauri/latest/tauri/), [tauri-runtime-wry Cargo.toml](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-runtime-wry/Cargo.toml), [docs.rs/wry](https://docs.rs/wry/latest/wry/)).

**Method note / caveat:** the `web_search` tool was broken in this environment (HTTP 401 on its search endpoint) for the whole session. All findings below come from pages and raw sources fetched directly (v2.tauri.app, docs.rs, raw.githubusercontent.com, developer.apple.com, bugs.webkit.org, man7.org, doc.rust-lang.org, nodejs.org, nixos.org) plus the GitHub issue/PR HTML. Where a claim rests only on a community report or on source code rather than documentation, it is marked. Claims marked **UNVERIFIED** could not be confirmed from any source I could reach.

---

## Bottom line

1. **Do not proxy the harness's HTTP/SSE traffic through a Tauri custom protocol.** Both protocol APIs take `http::Request<Vec<u8>>` and return a fully-buffered body; there is no streaming/chunked response API, and the tracking issue for one has been open since Sept 2023 ([wry #1022](https://github.com/tauri-apps/wry/issues/1022), [Builder docs](https://docs.rs/tauri/latest/tauri/struct.Builder.html#method.register_uri_scheme_protocol)). Tauri's own "streaming" example is HTTP `Range` handling over a buffered `Vec<u8>` ([examples/streaming/main.rs](https://github.com/tauri-apps/tauri/blob/dev/examples/streaming/main.rs)).
2. **Keep the Node harness's HTTP server.** Serve agents/streams from the child process on `127.0.0.1` and let the webview `fetch` it directly; just send the exact per-platform origin in `Access-Control-Allow-Origin` (`tauri://localhost` on macOS/Linux/iOS, `http://tauri.localhost` on Windows/Android, `https://…` if you opt into `useHttpsScheme`) ([app.rs](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri/src/app.rs), [use_https_scheme docs](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-utils/src/config.rs)). `http://127.0.0.1:PORT` is a *potentially trustworthy* origin, so it is not blocked as mixed content ([W3C Secure Contexts](https://w3c.github.io/webappsec-secure-contexts/#is-origin-trustworthy)).
3. **Sidecar auto-cleanup is narrower than most posts claim.** In v2, killing spawned children on `RunEvent::Exit` only happens for children spawned **from JavaScript** through the shell plugin's command handler; a child spawned from Rust via `app.shell().sidecar(...).spawn()` is *not* registered and will outlive the app ([shell lib.rs](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/shell/src/lib.rs), [shell commands.rs](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/shell/src/commands.rs)). If the parent is `SIGKILL`ed nothing runs at all, so parent-death detection must live in the child.
4. **On macOS, a bundled Node tree is your signing problem, not Tauri's.** Tauri's bundler signs `Contents/MacOS`, `Contents/Frameworks`, `PlugIns`, `Helpers`, `XPCServices`, `Libraries` — **never `Contents/Resources`** — and `codesign --deep` is deprecated for signing and likewise does not reach `Contents/Resources` ([macos/app.rs](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle/macos/app.rs), [codesign(1)](https://keith.github.io/xcode-man-pages/codesign.1.html)). Shipping Node in `Resources` + a thin launcher as `externalBin` works, but you must sign every nested Mach-O yourself; a real shipping project documents exactly this workflow ([conan docs/tauri-desktop.md](https://github.com/thewhatmatters/conan/blob/main/docs/tauri-desktop.md)).
5. **Distribution:** the v2 updater is minisign/Ed25519 over a full `.app.tar.gz`, usable outside the App Store; there is **no** official Homebrew tooling, and casks (custom tap) are the practical channel — a source formula is not.

## 1. Custom protocol / asset serving

### API surface and what the body types actually are

`Builder::register_uri_scheme_protocol` takes `Fn(UriSchemeContext<'_, R>, http::Request<Vec<u8>>) -> http::Response<T> where T: Into<Cow<'static, [u8]>>`; `register_asynchronous_uri_scheme_protocol` takes `Fn(UriSchemeContext<'_, R>, http::Request<Vec<u8>>, UriSchemeResponder)`, and the responder's only method is `respond<T: Into<Cow<'static, [u8]>>>(Response<T>)` ([Builder API](https://docs.rs/tauri/latest/tauri/struct.Builder.html#method.register_asynchronous_uri_scheme_protocol), [app.rs](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri/src/app.rs), [wry RequestAsyncResponder](https://docs.rs/wry/latest/wry/struct.RequestAsyncResponder.html)). Consequence: **the response body must be a contiguous in-memory buffer**; "asynchronous" only means the handler may reply later from another thread, not that it may stream.

### Can a handler receive the request body?

Yes on all three desktop backends — but always fully buffered:

| Platform | Webview | Request body delivered? | Mechanism |
|---|---|---|---|
| macOS / iOS | WKWebView | Yes, buffered | `request.HTTPBody()` / `HTTPBodyStream()` read into `Vec<u8>` ([wry url_scheme_handler.rs](https://github.com/tauri-apps/wry/blob/dev/src/wkwebview/class/url_scheme_handler.rs)) |
| Windows | WebView2 (Chromium) | Yes, buffered | `WebResourceRequest.Content()` drained into a `Vec<u8>` ([wry webview2/mod.rs](https://github.com/tauri-apps/wry/blob/dev/src/webview2/mod.rs)) |
| Linux | WebKitGTK | Yes, buffered | `request.http_body()` read in 1024-byte chunks into a `Vec<u8>`, behind wry's `linux-body` feature ([wry web_context.rs](https://github.com/tauri-apps/wry/blob/dev/src/webkitgtk/web_context.rs)) — Tauri enables that feature: `wry = { version = "0.56.0", default-features = false, features = ["os-webview", "linux-body"] }` ([tauri-runtime-wry Cargo.toml](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-runtime-wry/Cargo.toml)) |

Two caveats. First, **streaming request bodies are not available from the webview side**: `RequestInit.duplex` and `ReadableStream` request bodies are `false` for Safari in MDN browser-compat-data (i.e. not in stable WKWebView), and WebKit bug 319891 ("Implement FetchRequest duplex property") only landed in trunk on 2026-07-23 ([BCD api/Request.json](https://raw.githubusercontent.com/mdn/browser-compat-data/main/api/Request.json), [WebKit 319891](https://bugs.webkit.org/show_bug.cgi?id=319891)). I could not confirm which WebKit/Safari release, if any, has shipped it — **UNVERIFIED**. Second, `POST`ing a **Blob** to a custom scheme handler is still broken on WebKit: bug 197237, status NEW, P2, open since 2019-04-24 (I fetched and read the bug page directly) ([WebKit 197237](https://bugs.webkit.org/show_bug.cgi?id=197237)). Note this contradicts the common claim that WKWebView delivers no POST bodies at all — see "Conflicts" below.

### Streaming responses: not supported, and the workarounds

* No streaming/chunked responses: wry #1022 is an open tracking issue asking for a `hyper::Body`-like type that would allow `Stream<Item = Vec<u8>>` from a custom protocol handler; it has been open since 2023-09-10 ([wry #1022](https://github.com/tauri-apps/wry/issues/1022)).
* Tauri's documented mechanism for *streaming from Rust to the frontend* is `tauri::ipc::Channel`: "The Tauri channel is the recommended mechanism for streaming data such as streamed HTTP responses to the frontend" ([Calling Rust from the Frontend](https://v2.tauri.app/develop/calling-rust/)). That is an `invoke`-based channel, not an HTTP-shaped response, so it does not help an existing HTTP client inside the harness UI.
* Large-file/media access via the asset protocol uses HTTP `Range` (`206 Partial Content`, `Accept-Ranges: bytes`, multi-range muxed with `multipart/byteranges`) over a buffered body ([asset.rs](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri/src/protocol/asset.rs)); a multi-range correctness fix landed 2026-08-06 ([tauri #15838](https://github.com/tauri-apps/tauri/pull/15838)). Long-standing feature requests for genuinely memory-free resource loading remain open ([tauri #4133](https://github.com/tauri-apps/tauri/issues/4133)).
* If you want a real HTTP server in front of the webview, Tauri ships `tauri-plugin-localhost` — "Expose your app's assets through a localhost server instead of the default custom protocol", with the explicit warning that it "brings considerable security risks" ([Localhost plugin](https://v2.tauri.app/plugin/localhost/)). A local server proxy for dev/HTTP semantics is also an open upstream feature request ([tauri #11953](https://github.com/tauri-apps/tauri/issues/11953)).

### `tauri://localhost` / asset protocol, origins, CORS and secure contexts

* **App pages** are served from `tauri://localhost` on macOS/iOS/Linux and `http://tauri.localhost` on Windows/Android; `tauri.conf.json > app > windows[].useHttpsScheme` (default `false`) switches Windows/Android to `https://<scheme>.localhost`, and the docs warn that changing it relocates IndexedDB/cookies/localStorage ([app.rs origin comment](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri/src/app.rs), [config.rs](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-utils/src/config.rs)).
* **Asset protocol** URLs are built by `convertFileSrc(path, protocol = 'asset')`: `${protocol}://localhost/${encodeURIComponent(path)}` except on Windows/Android where it is `${protocolScheme}://${protocol}.localhost/${path}` ([core.js](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri/scripts/core.js)). It must be enabled and scoped: `app.security.assetProtocol.enable` + `scope` (glob list, `$HOME`/`$RESOURCE`-style base variables, `deny`, `requireLiteralLeadingDot` defaulting to `true` on Unix) ([Asset protocol scope](https://v2.tauri.app/security/asset-protocol/)).
* **CORS is real for custom schemes.** Tauri's own API doc warns: "Pages loaded from a custom protocol will have a different Origin on different platforms. Servers which enforce CORS will need to add the exact same Origin header (or `*`) in `Access-Control-Allow-Origin` if you wish to send requests with native `fetch` and `XmlHttpRequest` APIs", listing the per-platform origins above ([app.rs](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri/src/app.rs)). Tauri's own handlers comply: the asset and app protocols echo `Access-Control-Allow-Origin: <window_origin>` and expose `content-range` ([asset.rs](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri/src/protocol/asset.rs), [tauri protocol.rs](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri/src/protocol/tauri.rs)). CSP sources for these schemes are `asset:`, `http://asset.localhost`, `ipc:`, `http://ipc.localhost` ([CSP](https://v2.tauri.app/security/csp/)).
* **Secure context status differs per platform and is the weakest-documented area.** WebKitGTK is explicitly registered as secure — `register_uri_scheme_as_secure(name)` is called for every custom scheme, with the comment "Enable secure context" ([wry web_context.rs](https://github.com/tauri-apps/wry/blob/dev/src/webkitgtk/web_context.rs)). On Windows the app origin is `http://<scheme>.localhost`, and the Secure Contexts algorithm makes a host that "is `localhost` or ends with `.localhost`" potentially trustworthy, as does any host in `127.0.0.0/8` ([W3C Secure Contexts](https://w3c.github.io/webappsec-secure-contexts/#is-origin-trustworthy)). On macOS there is no equivalent call in wry, and the long-standing wry issue "Secure Context" — opening with "since code injection is none of these, we don't have a secure context" — is still open ([wry #10](https://github.com/tauri-apps/wry/issues/10)). I found no Tauri or wry documentation that states what `window.isSecureContext` returns for `tauri://localhost` on macOS, and I could not test it here: treat macOS secure-context-dependent APIs (`crypto.subtle`, service workers, `SharedArrayBuffer`) as **UNVERIFIED** and probe at runtime.
* **Live macOS risk to track:** wry #1778 reports that on macOS 26.6 beta 5, WKWebView stopped delivering cross-custom-scheme subresource requests to `WKURLSchemeHandler`, so a `tauri://localhost` page can no longer load `asset://localhost/...` images; the reporter reproduced it in pure Swift/WebKit 6.2.3 and the issue carries labels `platform: macOS`, `priority: high`, `status: upstream` with no comments as of today ([wry #1778](https://github.com/tauri-apps/wry/issues/1778)). Whether this persists in released macOS 26.6 is **UNVERIFIED** — I could not find a confirmation or fix.

## 2. Sidecar processes

### How `externalBin` / `Command::sidecar` work

* `bundle.externalBin` lists paths; for each target you must ship a file named `<name>-$TARGET_TRIPLE` (e.g. `binaries/my-sidecar-aarch64-apple-darwin`); current triple via `rustc --print host-tuple` (Rust ≥ 1.84) ([Embedding External Binaries](https://v2.tauri.app/develop/sidecar/)). On macOS the bundler copies each external binary into `Contents/MacOS` and signs it as an executable ([macos/app.rs](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle/macos/app.rs)).
* The shell plugin resolves a sidecar **relative to the running executable's directory** (`current_exe().parent()`), so at runtime the sidecar must sit next to the app binary — on macOS, `Contents/MacOS` — and the plugin strips/adds `.exe` on Windows ([process/mod.rs](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/shell/src/process/mod.rs)). Note this differs from `bundle.resources`, which lands in `Contents/Resources`.
* Rust usage is `app.shell().sidecar("my-sidecar")?.spawn()` → `(Receiver<CommandEvent>, CommandChild)`; `child.write(&[u8])` writes to stdin, `CommandEvent::Stdout/Stderr(Vec<u8>)` carry output, and by default output is split **on `\n` or `\r`** — switch to raw bytes with `set_raw_out(true)` if you need length-prefixed framing ([Embedding External Binaries](https://v2.tauri.app/develop/sidecar/), [process/mod.rs](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/shell/src/process/mod.rs)). Line-splitting makes NDJSON a natural fit out of the box.
* `Command::spawn` always creates fresh pipes for stdin/stdout/stderr; the plugin exposes `arg(s)`, `env`, `envs`, `env_clear`, `current_dir` — and **no way to inherit or pass extra file descriptors** ([process/mod.rs](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/shell/src/process/mod.rs)). This is the direct gap versus Electron's `stdio: ['ignore','pipe','pipe','pipe','pipe','ipc']` pattern: there is no built-in extra IPC fd. The equivalents are (a) NDJSON over the piped stdin/stdout, (b) a localhost socket/HTTP server in the child, or (c) dropping to raw `std::process::Command`, which does let you inherit stdio and, on Unix, set `process_group`/`pre_exec` ([std::os::unix::process::CommandExt](https://doc.rust-lang.org/std/os/unix/process/trait.CommandExt.html)). Node's own `fork()` IPC channel (`'ipc'` stdio entry, `disconnect` event) is the Electron-style mechanism and has no Tauri analogue ([Node child_process](https://nodejs.org/api/child_process.html)).
* `tauri-plugin-shell` vs raw `std::process::Command`: the plugin gives you sidecar path resolution, an async event stream, and JS-side spawn/kill commands; raw `Command` gives you fd/stdin inheritance, process groups and `pre_exec`, at the cost of doing path resolution and event plumbing yourself. Note v1's built-in `tauri::api::process::Command` is gone in v2 — sidecars now require the shell plugin ([v1 sidecar docs](https://v1.tauri.app/v1/guides/building/sidecar)).

### Killing reliably, and orphans

* What Tauri does for you: the shell plugin keeps a `ChildStore` and, on `RunEvent::Exit`, iterates it calling `child.kill()` ([shell lib.rs](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/shell/src/lib.rs)). **Only the JS-facing `spawn` command inserts into that store**; the Rust `Command::spawn` path does not ([shell commands.rs](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/shell/src/commands.rs) vs [process/mod.rs](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/shell/src/process/mod.rs)). This is a v1→v2 behavioural trap: a 2022 maintainer answer states sidecars get automatic cleanup ([discussion #3273](https://github.com/orgs/tauri-apps/discussions/3273)), which is not true of v2 Rust-side spawns.
* `RunEvent::Exit` is "Event loop is exiting" — it fires on a normal shutdown path, never when the process is `SIGKILL`ed ([RunEvent docs](https://docs.rs/tauri/latest/tauri/enum.RunEvent.html)). `CommandChild::kill` maps to `SharedChild::kill` → `Child::kill`, i.e. `SIGKILL` to the direct child on Unix and `TerminateProcess` on Windows; **grandchildren are not killed**, which is why "kill tree" is a requested feature ([process/mod.rs](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/shell/src/process/mod.rs), [tauri #14360](https://github.com/tauri-apps/tauri/issues/14360), [PR #14443](https://github.com/tauri-apps/tauri/pull/14443)). Earlier reports of the same class: [tauri #1896](https://github.com/tauri-apps/tauri/issues/1896), and the shell plugin's missing lifecycle features are enumerated in [plugins-workspace #3062](https://github.com/tauri-apps/plugins-workspace/issues/3062) (Oct 2025: crash restart, port conflicts, health checks, graceful shutdown, orphan cleanup, signal handling — all left to the app).
* For a long-lived supervised sidecar with SIGKILL-proof cleanup, the defensible design is: **(1)** kill from Rust on `RunEvent::Exit` *and* `ExitRequested`; **(2)** make the child self-terminate on parent death — watch stdin for EOF (the pipe closes when the parent dies), poll `getppid()`, or on Linux set `PR_SET_PDEATHSIG` in the child ([prctl(2)](https://man7.org/linux/man-pages/man2/prctl.2.html)); on macOS there is no `PDEATHSIG` equivalent, so EOF/`getppid`/`kqueue` polling is the portable choice; **(3)** if you use raw `std::process::Command`, put the sidecar in its own process group and signal the group so its children die too ([CommandExt::process_group](https://doc.rust-lang.org/std/os/unix/process/trait.CommandExt.html)); **(4)** keep a PID file or port lock so a relaunch can reap a stale instance — a community plugin (`tauri-plugin-sidecar`) exists precisely to implement this declaratively ([timo9378/tauri-plugin-sidecar](https://github.com/timo9378/tauri-plugin-sidecar)).
* **UNVERIFIED:** I found no official Tauri documentation page about orphan prevention or parent-death detection; the mechanisms above are generic OS/Node behaviour plus the source-level facts cited.

## 3. Bundling a Node.js runtime (macOS)

### What people actually do

The officially documented route is to *not* ship Node: Tauri's own guide recommends compiling the Node app to a self-contained binary with `pkg` (or similar) and shipping that as an `externalBin`, noting the alternative — "embed the Node runtime itself into your Tauri application and ship bundled JavaScript as a resource" — only as a second option ([Node.js as a sidecar](https://v2.tauri.app/learn/sidecar-nodejs/)). For a real harness with native addons, `pkg`-style single-file bundling is often not viable, so the "launcher + runtime tree in Resources" pattern is what ships in practice:

* A concrete, documented example: `src-tauri/binaries/<app>-gateway-<triple>` is a tiny relocatable launcher (an `externalBin`, so it lands in `Contents/MacOS`) that `exec`s `runtime/node runtime/gateway.cjs`; the `runtime/` tree (Node binary, bundled JS, and native addons as real files) is copied into the `.app` via `bundle.resources`, so the launcher reads it at `../Resources/runtime` ([conan docs/tauri-desktop.md](https://github.com/thewhatmatters/conan/blob/main/docs/tauri-desktop.md)). Tauri's resource docs confirm resources are placed under `$RESOURCE/` preserving structure ([Embedding Additional Files](https://v2.tauri.app/develop/resources/)), and the macOS bundler calls `settings.copy_resources(&resources_dir)` with `resources_dir = Contents/Resources` ([macos/app.rs](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle/macos/app.rs)).
* `bundle.macOS.files` is the escape hatch for arbitrary placement: "The files to include in the application relative to the Contents directory" ([config.rs](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-utils/src/config.rs), [macos/app.rs](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle/macos/app.rs)) — and, like `resources`, it is copied *without* being added to the signing list.

### How Tauri's macOS bundler signs nested binaries (source-verified)

* The bundler collects `SignTarget { path, is_an_executable }` for: frameworks copied into `Contents/Frameworks`, the main binary, and `externalBin` sidecars (`copy_binaries`/`copy_binaries_to_bundle` → `Contents/MacOS`). It then pushes the `.app` bundle itself last and signs — the source comment says "Sign frameworks and sidecar binaries first, per apple, signing must be done inside out" ([macos/app.rs](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle/macos/app.rs)).
* Recursion into nested code is driven by a fixed folder list: `NESTED_CODE_FOLDER = ["MacOS", "Frameworks", "Plugins", "Helpers", "XPCServices", "Libraries"]`. Inside those, only `.framework`, `.xpc`, `.app`, `.dylib` and **extension-less** files are signed; a `.node` addon (extension `node`) is skipped ([macos/app.rs](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle/macos/app.rs)). `Contents/Resources` is not in the list at all, and `copy_resources` is never added to `sign_paths`.
* Each target is signed with `codesign --force -s <identity> [--options runtime] [--entitlements <plist>] <path>`; `--options runtime` is applied when `is_an_executable && bundle.macOS.hardenedRuntime` ([tauri-macos-sign keychain.rs](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-macos-sign/src/keychain.rs), [bundle/macos/sign.rs](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle/macos/sign.rs)). Before signing, the bundle is stripped of extended attributes with `xattr -crs <app>` ([macos/app.rs](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle/macos/app.rs)); the source cites Apple's [QA1940](https://developer.apple.com/library/archive/qa/qa1940/_index.html).
* Notarization, when credentials are present, is `xcrun notarytool submit … ` followed by `xcrun stapler staple` ([tauri-macos-sign lib.rs](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-macos-sign/src/lib.rs)); credentials come from `APPLE_ID`/`APPLE_PASSWORD`/`APPLE_TEAM_ID` or an App Store Connect API key ([sign/macos.rs](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle/macos/sign.rs), [macOS Code Signing](https://v2.tauri.app/distribute/sign/macos/)).

**Net effect:** anything you put in `Contents/Resources` — i.e. the whole Node runtime tree — is invisible to Tauri's signing and to `--deep`. The `codesign` man page is explicit that `--deep` is "(DEPRECATED for signing as of macOS 13.0)", that it applies all signing options to nested content ("This is almost never what you want"), and that it only discovers nested code in `Contents`, `Contents/Frameworks`, `Contents/SharedFrameworks`, `Contents/PlugIns`, `Contents/Plug-ins`, `Contents/XPCServices`, `Contents/Helpers`, `Contents/MacOS`, `Contents/Library/...` — "If any code (Mach-Os, bundles) are located outside the above listed locations they will not be signed by the --deep option" ([codesign(1)](https://keith.github.io/xcode-man-pages/codesign.1.html)).

### What breaks, and whether Node + addons can be notarized

* Signing order and per-file signatures are on you. The conan release script signs "**every** Mach-O under `runtime/` (the `.node` addons, `spawn-helper`, the embedded `node`, the launcher)" with Developer ID + `--options runtime` + `--timestamp` + entitlements, because "Apple's notarization scans recursively and rejects any nested binary missing a Developer ID sig, secure timestamp, or hardened runtime" ([conan docs](https://github.com/thewhatmatters/conan/blob/main/docs/tauri-desktop.md)). Apple's notary service does scan the whole submitted archive; the classic failure is `"The signature of the binary is invalid."` ([Apple: Notarizing macOS software](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)).
* That failure is not hypothetical for sidecars: tauri #11992 (open since Dec 2024) reports notarization failing with `"The signature of the binary is invalid."` on `Contents/MacOS/<app>` **as soon as any `externalBin` sidecar is added**, in a minimal repro project, with `hardenedRuntime: true`; the log shows the bundler signing the sidecar and the app with `--options runtime` before submitting ([tauri #11992](https://github.com/tauri-apps/tauri/issues/11992)). Related older reports: [#9422](https://github.com/tauri-apps/tauri/issues/9422) (cannot bundle external binaries on macOS), [#11261](https://github.com/tauri-apps/tauri/issues/11261) (Node single-executable binary works in dev, not in production).
* **Library validation is the native-addon killer.** Hardened runtime "enables library validation by default … [which] prevents a program from loading frameworks, plug-ins, or libraries unless they're either signed by Apple or signed with the same Team ID as the main executable" ([Apple: Disable Library Validation Entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.disable-library-validation)). npm-shipped `.node` addons are signed by their packagers, not by you, so the shipped app needs `com.apple.security.cs.disable-library-validation`; the conan entitlements table lists exactly that, plus `allow-jit`/`allow-unsigned-executable-memory` for WKWebView's JIT and `com.apple.security.cs.allow-dyld-environment-variables` for `node-pty`'s `spawn-helper`, and notes Apple flags new entitlements per submission ([conan docs](https://github.com/thewhatmatters/conan/blob/main/docs/tauri-desktop.md)). Apple warns Gatekeeper runs extra checks on apps that disable library validation ([Apple entitlement page](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.disable-library-validation)).
* **Known to work?** Yes, in at least one documented production case: the conan project ships a Node gateway with `better-sqlite3` and `node-pty` inside a Tauri v2 `.app`, producing a stapled/notarized `.app` + `.dmg` (`Conan.app` ≈ 189 MB, `.dmg` ≈ 56 MB) via a custom `release` script, and it verifies both with `spctl --assess` reading `source=Notarized Developer ID` ([conan docs](https://github.com/thewhatmatters/conan/blob/main/docs/tauri-desktop.md)). Note the workflow is **outside** Tauri's built-in notarization: they re-sign, re-zip, submit with `notarytool --wait`, staple, then rebuild the `.dmg` from the stapled `.app` because Tauri's DMG predates the staple.
* Other macOS gotchas from the same report and sources: ad-hoc signing (`codesign -s -`) of the launcher and embedded `node` is needed just to launch locally on Apple silicon ([conan docs](https://github.com/thewhatmatters/conan/blob/main/docs/tauri-desktop.md)); any process writing inside the bundle between sign and notarize invalidates the seal (their case: a live gateway writing to `Contents/Resources/.claude/`); quarantine attributes on downloaded apps are handled by Tauri's `xattr -crs` at build time ([macos/app.rs](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle/macos/app.rs), [QA1940](https://developer.apple.com/library/archive/qa/qa1940/_index.html)) — but a quarantined `.dmg`/`.app` still gets Gatekeeper's first-launch prompt; **DYLD_\* variables are ignored for hardened-runtime processes unless the `allow-dyld-environment-variables` entitlement is present**, which is why relative-path resolution inside the runtime tree (not `DYLD_LIBRARY_PATH`) is the reliable approach ([conan docs](https://github.com/thewhatmatters/conan/blob/main/docs/tauri-desktop.md) documents the entitlement's necessity; I did not find an Apple page stating the DYLD stripping rule verbatim — **partially UNVERIFIED**).

## 4. Updater and distribution channels

*(Researched in parallel; version baseline `tauri` 2.11.5, `tauri-plugin-updater` 2.11.0.)*

* **Artifacts:** `bundle.createUpdaterArtifacts` is a `bool | "v1Compatible"` field (default `false`) — **not** a bundle target; I verified in `config.rs` that `BundleType` has exactly `Deb, Rpm, AppImage, Msi, Nsis, App, Dmg` and no `updater` variant ([config.rs](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-utils/src/config.rs), [config reference](https://v2.tauri.app/reference/config/)). With `true`, macOS emits `MyApp.app.tar.gz` + `.sig`; Windows signs the NSIS `.exe`/MSI; Linux signs the `.AppImage`. Updater bundles are only emitted for macOS-bundle targets, so a **dmg-only build silently yields no updater artifacts** ([updater docs](https://v2.tauri.app/plugin/updater/), [tauri-bundler bundle.rs](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle.rs)). `"v1Compatible"` produces zipped variants and is deprecated for v3 ([updater docs](https://v2.tauri.app/plugin/updater/)).
* **Signatures:** minisign/Ed25519. The plugin verifies with `minisign_verify`, and the CLI depends on `minisign = "0.9"` with an in-repo comment warning that upgrading it has broken updater signatures before ([updater.rs](https://raw.githubusercontent.com/tauri-apps/plugins-workspace/v2/plugins/updater/src/updater.rs), [tauri-cli Cargo.toml](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-cli/Cargo.toml)). Keys: `tauri signer generate`; build-time signing needs `TAURI_SIGNING_PRIVATE_KEY` (+ `_PASSWORD`) as real env vars — `.env` files do not work ([updater docs](https://v2.tauri.app/plugin/updater/)).
* **Manifest:** static JSON with `version`, `notes`, `pub_date`, `platforms.<key>.{signature,url}`; docs list `OS-ARCH` keys (`darwin-aarch64`), but the implementation resolves `{os}-{arch}-{installer}` first and falls back to `{os}-{arch}`, so `darwin-aarch64-app` is valid, and there is an undocumented `{{bundle_type}}` URL variable ([updater docs](https://v2.tauri.app/plugin/updater/), [updater.rs](https://raw.githubusercontent.com/tauri-apps/plugins-workspace/v2/plugins/updater/src/updater.rs), [tauri-action upload-version-json.ts](https://raw.githubusercontent.com/tauri-apps/tauri-action/dev/src/upload-version-json.ts)). Config keys under `plugins.updater`: `pubkey` (inline content, cannot be a path), `endpoints`, `dangerousInsecureTransportProtocol`, `windows.installMode` (`passive` default / `basicUi` / `quiet`) ([updater docs](https://v2.tauri.app/plugin/updater/)).
* **Full-bundle replacement, not a patch:** on macOS the updater extracts `MyApp.app.tar.gz`, renames the running `.app` aside, moves the extracted tree in, and falls back to an AppleScript `rm -rf … && mv -f … with administrator privileges` on permission errors — so a read-only location (running from the DMG) is not supported ([updater.rs](https://raw.githubusercontent.com/tauri-apps/plugins-workspace/v2/plugins/updater/src/updater.rs), [updater_bundle.rs](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle/updater_bundle.rs)). This is ordinary https-endpoint distribution and works outside the App Store; the App Store path instead requires sandboxing and a signed `.pkg` ([App Store docs](https://v2.tauri.app/distribute/app-store/)). Whether the updater is *incompatible* with the Mac App Store is not stated by Tauri — **inference from the sandbox requirement, not documentation**.
* **`tauri build` on macOS** produces `.app` in `target/<profile>/bundle/macos/` and `.dmg` in `target/<profile>/bundle/dmg/` ([macos/app.rs](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle/macos/app.rs)). A dmg build in a headless CI session needs `CI=true` (Tauri passes `--sandbox-safe`, skipping the Finder AppleScript step that otherwise times out with `AppleEvent timed out (-1712)`) ([conan docs](https://github.com/thewhatmatters/conan/blob/main/docs/tauri-desktop.md)).
* **Homebrew:** there is no official Tauri Homebrew tooling or docs page (the Distribute nav lists AUR but not Homebrew), and `tauri-action` exposes no cask step ([Distribute](https://v2.tauri.app/distribute/), [tauri-action README](https://raw.githubusercontent.com/tauri-apps/tauri-action/dev/README.md)). `latest.json` carries no sha256, so cask checksums must be computed from the `.dmg` yourself ([upload-version-json.ts](https://raw.githubusercontent.com/tauri-apps/tauri-action/dev/src/upload-version-json.ts)). In practice Tauri apps are distributed as casks in custom taps: homebrew-cask contains e.g. `clash-verge-rev` (per-arch dmg sha256, `zap` stanza) and `gitbutler` (uses the updater artifact `GitButler.app.tar.gz` as the cask `url`) ([clash-verge-rev.rb](https://raw.githubusercontent.com/Homebrew/homebrew-cask/master/Casks/c/clash-verge-rev.rb), [gitbutler.rb](https://raw.githubusercontent.com/Homebrew/homebrew-cask/master/Casks/g/gitbutler.rb)). Homebrew policy directs GUI software with compiled releases to casks, and homebrew-core's `formula.json` contains zero formulae mentioning "tauri" (formula/tauri.json etc. return 404) — so a **source formula is not practical** ([Acceptable Casks](https://docs.brew.sh/Acceptable-Casks)).

## 5. Nix packaging

*(Researched in parallel; nixpkgs master / 25.05 / 25.11 checked.)*

* **The supported mechanism is a setup hook, not a builder.** nixpkgs ships `cargo-tauri`, whose `passthru` exposes `hook` and `gst-plugin`; the hook is documented at `doc/hooks/tauri.section.md` and exists on `release-25.05`, `release-25.11` and `master` ([cargo-tauri package.nix](https://raw.githubusercontent.com/NixOS/nixpkgs/master/pkgs/by-name/ca/cargo-tauri/package.nix), [nixpkgs manual: Tauri hook](https://nixos.org/manual/nixpkgs/unstable/#tauri-hook)).
* **There is no `tauriBundle`/`buildTauriApp` in nixpkgs** — `all-packages.nix` on master contains zero occurrences of "tauri" (by-name packages are auto-called), and the Rust section of the manual never mentions Tauri. `buildTauriApp` exists only in the third-party flake [JPHutchins/crane-tauri](https://raw.githubusercontent.com/JPHutchins/crane-tauri/main/README.md) — do not describe it as a nixpkgs helper.
* The hook sets `dontCargoBuild`/`dontCargoInstall`, installs `tauriBuildHook`/`tauriInstallHook`/`tauriFixupHook`, and runs `cargo tauri build --bundles <type> --target <spec> -- -j $NIX_BUILD_CORES --target <spec> --offline`; it appends `build.target-dir` to `config.toml` because Tauri ignores `CARGO_TARGET_DIR`. Bundle-type defaults are `darwin = "app"`, `linux = "deb"`, and on Darwin the install phase moves `bundle/macos/*.app` into `$out/Applications`. Tunables: `tauriBuildFlags`, `tauriBundleType`, `dontTauriBuild`, `dontTauriFixup`, `dontTauriInstall` ([hook.nix](https://raw.githubusercontent.com/NixOS/nixpkgs/master/pkgs/by-name/ca/cargo-tauri/hook.nix), [hook.sh](https://raw.githubusercontent.com/NixOS/nixpkgs/master/pkgs/by-name/ca/cargo-tauri/hook.sh)).
* Real in-tree examples: [`cc-switch`](https://raw.githubusercontent.com/NixOS/nixpkgs/master/pkgs/by-name/cc/cc-switch/package.nix) uses `cargo-tauri.hook` + `fetchPnpmDeps` + `pnpmConfigHook` + `nodejs` + `pnpm_10` with `cargoRoot`/`buildAndTestSubdir = "src-tauri"`; [`deltachat-tauri`](https://raw.githubusercontent.com/NixOS/nixpkgs/master/pkgs/by-name/de/deltachat-tauri/package.nix) is the Darwin counterpart using `apple-sdk_14` and `darwin.autoSignDarwinBinariesHook` (and is currently marked `broken` for Tauri version mismatches).
* **pnpm attribute naming is version-critical:** the current attrs are `pnpm_9`, `pnpm_10`, `pnpm_11` (underscore form, no `pnpm-10`), and `fetchPnpmDeps`/`pnpmConfigHook` **do not exist in nixpkgs 25.05**, which only documents the older `pnpm_9.fetchDeps`/`configHook` API ([25.05 JS manual](https://raw.githubusercontent.com/NixOS/nixpkgs/release-25.05/doc/languages-frameworks/javascript.section.md), [25.11 JS manual](https://raw.githubusercontent.com/NixOS/nixpkgs/release-25.11/doc/languages-frameworks/javascript.section.md)). `fetcherVersion` differs between packages (3 vs 4) — copy the value from the branch you target.
* **`beforeBuildCommand` in the sandbox is a real problem.** `cargo tauri build` runs the hook, which would try `pnpm install` with no network, and `frontendDist` must exist *before* the Rust build (tauri-codegen panics "The `frontendDist` configuration is set to `{path:?}` but this path doesn't exist"; the CLI errors "Unable to find your web assets, did you forget to build your web app?"). cc-switch's comment states it plainly — it strips the command in `postPatch` (`jq 'del(.build.beforeBuildCommand)'`) and runs `pnpm run build:renderer` in `preBuild`; the cleaner alternative is injecting `frontendDist` via `--config`/`TAURI_CONFIG` ([tauri-cli build.rs](https://raw.githubusercontent.com/tauri-apps/tauri/dev/crates/tauri-cli/src/build.rs), [tauri-cli helpers/config.rs](https://raw.githubusercontent.com/tauri-apps/tauri/dev/crates/tauri-cli/src/helpers/config.rs), [tauri-build lib.rs](https://raw.githubusercontent.com/tauri-apps/tauri/dev/crates/tauri-build/src/lib.rs), [cc-switch package.nix](https://raw.githubusercontent.com/NixOS/nixpkgs/master/pkgs/by-name/cc/cc-switch/package.nix)).
* `TAURI_SKIP_DEVSERVER_CHECK` is obsolete (renamed to `TAURI_CLI_NO_DEV_SERVER_WAIT`, and it concerns dev-server waiting only) ([ENVIRONMENT_VARIABLES.md](https://raw.githubusercontent.com/tauri-apps/tauri/dev/crates/tauri-cli/ENVIRONMENT_VARIABLES.md)). On Darwin, nixpkgs deliberately avoids DMG (`app` only; the DMG script depends on `hdiutil`/`SetFile`, which nixpkgs patches) — an `hdiutil`-unavailable failure specifically is **UNVERIFIED** ([PR #499908](https://github.com/NixOS/nixpkgs/pull/499908.diff), [PR #490155](https://github.com/NixOS/nixpkgs/pull/490155.diff)). Linux inputs in real expressions: `webkitgtk_4_1`, `libsoup_3`, `glib-networking`, `libayatana-appindicator`, `openssl`, `pkg-config`, `wrapGAppsHook3` ([cc-switch](https://raw.githubusercontent.com/NixOS/nixpkgs/master/pkgs/by-name/cc/cc-switch/package.nix), [Prerequisites](https://v2.tauri.app/start/prerequisites/)). `dream2nix` has no Tauri support; the NixOS wiki page defers to the nixpkgs manual ([NixOS Wiki: Tauri](https://wiki.nixos.org/wiki/Tauri)).

## 6. Alternatives worth noting

* **wry + tao directly:** usable standalone — Tauri's own docs say "TAO is responsible for Tauri window creation and WRY is responsible for web view rendering. These are libraries maintained by Tauri and can be consumed directly" ([What is Tauri?](https://v2.tauri.app/start/), [Architecture](https://v2.tauri.app/concept/architecture/)). You forgo the bundler, CLI, asset embedding/CSP injection, the capability/ACL permission system and the updater. wry exposes `with_custom_protocol` and `with_asynchronous_custom_protocol` with the same buffered `Cow<'static, [u8]>` response type — no streaming there either ([WebViewBuilder](https://docs.rs/wry/latest/wry/struct.WebViewBuilder.html), [RequestAsyncResponder](https://docs.rs/wry/latest/wry/struct.RequestAsyncResponder.html)).
* **Minimal app size:** the usually-quoted figure is on the quick-start page — "a minimal Tauri app can be **less than 600KB** in size", justified by the system webview ([What is Tauri?](https://v2.tauri.app/start/)). The size page itself contains only Cargo profile tuning, no number ([App Size](https://v2.tauri.app/concept/size/)). The figure is unqualified as to bare executable vs `.app` bundle and excludes WKWebView (a system framework) — treat it as order-of-magnitude, and note a real-world V1→V2 report of ~3 MiB → 6.2 MiB ([tauri #12820](https://github.com/tauri-apps/tauri/issues/12820), anecdotal). A bundled Node runtime will dominate: the conan example ships a 189 MB `.app`.
* **WKWebView streaming limitations that matter here:** response streaming in JS works (`Response.body`/`ReadableStream` since Safari 10.1, `TextDecoderStream` 14.1+), so SSE-over-`fetch` from a real HTTP server is viable ([BCD api/Response.json](https://raw.githubusercontent.com/mdn/browser-compat-data/main/api/Response.json)); `fetch` *request* streaming (`duplex: 'half'`) is not in stable Safari/WKWebView ([BCD api/Request.json](https://raw.githubusercontent.com/mdn/browser-compat-data/main/api/Request.json), [WebKit 319891](https://bugs.webkit.org/show_bug.cgi?id=319891)); `EventSource` itself exists since Safari 5 ([BCD api/EventSource.json](https://raw.githubusercontent.com/mdn/browser-compat-data/main/api/EventSource.json)). The binding constraint in Tauri is architectural, not the engine: custom-scheme responses cannot stream, so SSE must be served over real HTTP ([wry #1022](https://github.com/tauri-apps/wry/issues/1022), [wry #1404](https://github.com/tauri-apps/wry/issues/1404), [tauri #13069](https://github.com/tauri-apps/tauri/issues/13069)). Other traps: `showOpenFilePicker` and friends are unsupported in Safari/WKWebView; `SharedArrayBuffer` needs a secure context plus cross-origin isolation; adding `WKAppBoundDomains` puts WKWebView into a mode that denies JavaScript injection and `window.webkit.messageHandlers` — the very machinery Tauri/wry rely on ([WebKit blog: App-Bound Domains](https://webkit.org/blog/10882/app-bound-domains/)). For a sandboxed app (App Store), `com.apple.security.network.client` is what permits outgoing connections, explicitly including to a server on the same machine ([Apple entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.network.client)).
* I could not find any macOS-WKWebView-specific SSE buffering bug; the EventSource bugs that exist are unrelated to buffering ([119974](https://bugs.webkit.org/show_bug.cgi?id=119974), [113748](https://bugs.webkit.org/show_bug.cgi?id=113748)). **Do not assert an SSE-buffering bug** — the defensible statement is the Tauri protocol limitation above.

## Conflicts, ambiguities, and things I could not verify

**Where sources conflict**

1. **"No POST bodies to custom schemes on WKWebView" is wrong.** wry's macOS handler reads `HTTPBody`/`HTTPBodyStream` into a `Vec<u8>`, and WebKit bug 191362 (missing XHR POST bodies) was fixed in 2019; the accurate remaining limitation is Blob bodies (bug 197237, still NEW) ([wry handler](https://github.com/tauri-apps/wry/blob/dev/src/wkwebview/class/url_scheme_handler.rs), [WebKit 191362](https://bugs.webkit.org/show_bug.cgi?id=191362), [WebKit 197237](https://bugs.webkit.org/show_bug.cgi?id=197237)). Any older blog post claiming otherwise is outdated.
2. **"Tauri uses `codesign --deep`" is not what the current bundler does.** `tauri-bundler` walks `SignTarget`s and signs each path inside-out, then the bundle ([macos/app.rs](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle/macos/app.rs)); the conan project's doc describes "Tauri's `--deep` re-sign" ([conan docs](https://github.com/thewhatmatters/conan/blob/main/docs/tauri-desktop.md)). The distinction matters: `--deep` is deprecated for signing, applies all options to nested content, and never reaches `Contents/Resources` ([codesign(1)](https://keith.github.io/xcode-man-pages/codesign.1.html)).
3. **Sidecar auto-kill on exit (v1-era advice) does not hold for v2 Rust spawns.** The v2 plugin's exit hook only drains `ChildStore`, which only the JS spawn command populates ([shell lib.rs](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/shell/src/lib.rs), [commands.rs](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/shell/src/commands.rs), cf. [discussion #3273](https://github.com/orgs/tauri-apps/discussions/3273)).
4. **Updater docs vs implementation:** docs list `OS-ARCH` platform keys and a fixed set of URL variables; the implementation accepts `{os}-{arch}-{installer}` and `{{bundle_type}}` ([updater docs](https://v2.tauri.app/plugin/updater/), [updater.rs](https://raw.githubusercontent.com/tauri-apps/plugins-workspace/v2/plugins/updater/src/updater.rs)).

**Ambiguous or undocumented**

* macOS `window.isSecureContext` for `tauri://localhost`: no documentation; WebKitGTK is explicitly secure, Windows `*.localhost` is spec-trustworthy, macOS has no equivalent registration and wry's "Secure Context" issue is still open ([wry #10](https://github.com/tauri-apps/wry/issues/10)). Probe at runtime before depending on `crypto.subtle`/service workers/`SharedArrayBuffer`.
* Whether the macOS 26.6 beta cross-scheme regression ([wry #1778](https://github.com/tauri-apps/wry/issues/1778)) shipped in the release — unknown; it would break `asset://` images in any Tauri app on that OS version.
* Whether Tauri's updater is permitted/incompatible under the Mac App Store: not documented either way; inference from the sandbox + `.pkg` requirement.
* Updater self-replacement constraints on macOS (writable location, xattrs, `/Applications`) are only visible in source, not docs.

**Explicitly unverified**

* Which Safari/WebKit release first ships `RequestInit.duplex` (trunk landed 2026-07-23; MDN still says preview).
* No measured minimal Tauri v2 macOS bundle size exists in the docs; the 600KB figure's scope is unstated.
* No documented macOS-specific SSE buffering bug could be found.
* No official Tauri guidance on orphan prevention/parent-death detection; the recommended mechanisms are generic OS behaviour.
* Whether AppImage/Flatpak bundle `webkit2gtk` and at what size cost.
* `hdiutil` unavailability inside the Nix darwin sandbox specifically (what *is* verified is that nixpkgs patches Tauri's DMG script and defaults to `app`).
* Whether a bundled Node runtime has ever been notarized *through Tauri's built-in notarization path alone* — the one detailed public report uses a custom post-sign/re-zip/notarize/staple script ([conan docs](https://github.com/thewhatmatters/conan/blob/main/docs/tauri-desktop.md)).

### Practical recommendation summary for this shell

| Need | Recommendation |
|---|---|
| Harness HTTP/SSE to UI | Keep the child's HTTP server on `127.0.0.1`; set `Access-Control-Allow-Origin` to the exact platform origin; optionally `tauri-plugin-localhost` for static assets |
| Rust→UI streaming | `tauri::ipc::Channel` (not a custom protocol) |
| Spawn/supervise Node | `externalBin` launcher in `Contents/MacOS` + runtime tree in `bundle.resources`/`bundle.MacOS.files` |
| Shutdown | Kill on `RunEvent::Exit`/`ExitRequested` **and** child-side stdin-EOF/`getppid` watchdog; raw `Command` + process group if the child forks |
| macOS signing | Sign every Mach-O under `Resources` yourself (Developer ID, `--options runtime`, `--timestamp`); expect `disable-library-validation`; budget a custom notarize/staple/DMG script |
| Updates | Updater plugin (minisign, full `.app.tar.gz`), custom tap cask for Homebrew |
| Nix | `cargo-tauri.hook`, strip `beforeBuildCommand`, `app` bundle only on darwin |
